发现一个具体的正确性/恢复问题（其余交叉项复核干净）：

src/preprocess/transcribe_mmlifelong_magic.py:44-45，配合写盘路径 :130-134 与恢复判断 :80。当某个 whisper 段落的 segment.text.strip() 为空字符串时（large-v3-turbo 在 VAD 边界可能产出空文本段，脚本没有过滤），JSON 会写入 "text": ""（能通过校验，因为只检查 isinstance str）；但对应 SRT 块写成 [序号, 时间戳, ""] 再加块间空行分隔（:115-121）。经过 handle.read().strip() 后按 "\n\n" 切分，那个空文本行与块间空行无法区分被吞掉，块只剩两行，于是 validate_complete 在 if len(block) < 3 处抛 ValueError。由于 json 和 srt 是在 :130-133 先写盘、:134 才校验，文件已经落地；再次运行时 :80 的恢复判断看到两个文件都在，又调用 validate_complete 再次抛错，这个视频无法完成，形成恢复死锁。真正无语音的视频（0 段 → 空 JSON + 空 SRT）不受影响，两侧长度都为 0，正常通过。这个是否触发取决于本次重新转录是否真的产出空文本段；ASR.txt 记录上一轮完整运行时所有段文本非空，因此命中概率属中等，但一旦命中就是整个 ASR 作业级别的失败点。

复核为无问题的项：转录脚本在导入 faster_whisper 之前于模块顶层设 CUDA_VISIBLE_DEVICES=1,4,5,6，spawn 子进程重新导入模块会在 CUDA 初始化前重新应用，device_index 0..3 映射到物理 1,4,5,6，正确；ASR 输出路径与 load_catalog 中 month/day/week 的 transcript_path 完全一致；row_id 格式与 build_full_magic_index.py:343 的 int(row_id.rsplit(":",1)[1]) 解析一致；week 源片段与 clip 的 zip(strict) 一一对应成立（build_full_video_database 每个片段建一个 clip，week 不被 cache_video_clips 删改，排序口径一致）；build_full_index_database 全部 13 处 INSERT 占位符数与 schema.sql 列数逐一吻合；chunk_times 无 KeyError 风险；location 与 chain_type 的 NULL 处理有保护，week 显式置 None；week 时钟到时间线映射按源 video_id 建段、越界抛 ValueError 走 LocalModel.generate 的重试校验路径，week_day/local_clock_start_sec/local_start_time 等键在后续读取的每个阶段都已写入；TopicFact/WeekTopicFact 的时间在入库前已校验为 HH:MM:SS 或映射回 HH:MM:SS，parse_hms 可解析；run_jobs 的补跑轮与按 shard 存在性恢复、末尾对缺失样本抛错的逻辑自洽。
