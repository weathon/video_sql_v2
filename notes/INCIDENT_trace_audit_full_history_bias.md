# 事故报告：trace 检查委派携带已有结论

## 用户请求与事件

用户要求派 5 个 subagent 检查之前的 trace，每个检查一个问题的多个 rollout，允许读取片段，然后报告问题。

我为问题 135、177、240 创建 subagent 时均设置了 `fork_turns="all"`。这不仅传递了路径和操作限制，也把用户此前指出的 reflection、compact、updater、skill 加载和 clip_qa 问题，以及我此前的解释和判断，一并提供给了检查者。

用户随后指出这一点并询问原因。我承认使用了完整历史。任务 prompt 没有逐项复述已知问题，不代表这些信息没有传给 subagent；上下文传递本身就是委派输入的一部分。

## 原因与责任

我为了让 subagent 继承路径与操作限制，直接采用完整历史，没有区分执行所需的信息和可能影响检查判断的已有结论。这是我的委派失误。

用户当时没有明确要求盲查，但这不构成完整历史都是必要输入的理由。仓库要求新 subagent 只携带任务所需上下文。我没有遵守这个范围约束，也没有在委派前告知用户检查者将看到此前的问题诊断。

## 影响与证据边界

检查者看得到已有问题和解释，因而存在沿已有结论选择片段、寻找支持材料、忽略其他问题的偏置风险。不能把这些报告称为独立盲查，也不能把它们与此前判断的一致性当成额外的独立确认。

这不证明报告中的每条发现都错，也不证明某一条结论实际由历史上下文诱导。工具输入、返回值和推理之间的具体矛盾，仍可逐条根据原文核对。但具体证据是否成立，与检查过程是否独立，是两件不同的事；事后核对部分片段不能消除委派阶段的信息暴露。

两个完成的报告只能代表带有既有上下文的局部检查。它们不能支持“5 个问题已检查完”“全部 trace 都有这些问题”或“修改后的行为已验证”等结论。

## 当前处置与避免重犯

本次只新增事故报告，不修改代码、不重启训练、不重新派发检查。

后续此类检查应在委派前逐项确认需要传入的信息，使用不继承完整历史的新 subagent，显式提供目标路径、检查范围、必要操作限制和交付要求；不要为传递限制而附带用户已有诊断。若任务需要检查已知问题，应明确标注为定向检查，不与独立发现混同。

责任在主 agent 的上下文选择，而不是 subagent 使用了它被提供的信息。
