# 事故报告：没有使用 vLLM 官方视觉编码拆分实现

日期：2026-09-03

责任方：Codex assistant

## 摘要

在补全根目录 `INFRA.txt` 的 Next Flash FP8 配置时，我没有先完整核对 vLLM 官方视觉编码拆分实现，而是沿用了仓库中过去的实验方案：自制 `infra/responses_epd_proxy.py`、`ECExampleConnector`、写入 `/raid` 的共享目录以及在活跃 Responses 请求数归零后清空目录。用户要求的是由 vLLM 原生参数启用官方实现，不需要自行实现磁盘保存和缓存生命周期管理。

## 经过

1. 我从旧提交和现有代理代码中复制了视觉编码服务、主模型服务和代理的拓扑。
2. 我把视觉编码结果的跨请求缓存与复用误解成需要由项目自行写入磁盘。
3. 我将 `/raid/wg25r/video_sql_v2/formal_runs/next_flash_fp8_epd_shared` 写成共享目录，并保留了代理在活跃请求归零后删除缓存的逻辑。
4. 用户追问为什么要保存视觉编码器结果时，我先用进程间传输解释这项设计，没有先回到官方实现核对。
5. 用户给出官方文档后，我才确认官方缓存的目的是跨请求复用；活跃请求归零就清空会直接破坏这种复用。
6. 我随后仍然把官方数据传输抽象错误地等同于磁盘缓存，直到用户指出官方实现可以由原生参数直接启用。

## 同次配置中的其他错误

1. 我最初提出让 Next Flash 使用 tensor parallel size 2，忽略了此前该配置没有可用 key-value cache 的已知结果；用户指出后才改为 tensor parallel size 4。
2. 我把“视觉编码服务和 embedding 服务共用一张独立 GPU”误解成两项服务各自独占一张 GPU；用户指出后才改回两项服务共同使用 GPU 4、各占 0.45。
3. Docker 命令沿用了 `--rm`，没有重新检查容器生命周期要求。
4. 计划中使用了没有展开说明的 “PD” 缩写，导致服务职责不清楚。

## 影响

- `INFRA.txt` 和 `PLANS.md` 提交了不符合用户指定实现的基础设施方案。
- 如果执行该方案，项目会维护不需要的自制代理、磁盘缓存目录和清理逻辑。
- 活跃请求归零时删除视觉编码结果会取消官方方案要求的跨请求复用。
- `--rm` 会在容器停止后自动删除容器，不符合当前容器保留要求。
- 本次错误尚未启动正式运行，因此没有产生错误实验结果。

## 根因

1. 我从旧代码和旧提交反推当前方案，而没有先从用户指定的官方实现确定最小正确配置。
2. 我没有把继承的代理、连接器、共享路径、清理逻辑和 Docker 参数逐项视为待验证配置。
3. 我在没有读完官方实现说明时就解释设计合理性，用推测维护了既有方案。
4. 我把“官方支持缓存和复用”错误扩展成“项目需要自行实现磁盘持久化和清理”。

## 正确方案

1. 使用 vLLM 原生的 `--ec-transfer-config` 配置官方视觉编码结果传输和缓存机制。
2. 不由本项目实现视觉编码结果的磁盘保存、共享目录生命周期或活跃请求归零清理。
3. 视觉编码服务与 embedding 服务共同使用独立于主模型服务的 GPU 4，各使用 0.45；主模型服务在 GPU 0、2、5、7 上使用 tensor parallel size 4。
4. Docker 容器启动命令不得包含 `--rm`，运行结束后再显式删除容器。
5. 文档中写完整服务职责，不使用未解释的缩写。

## 防止再次发生

1. 用户指定官方实现时，先完整读取官方功能说明和启动方式，再检查本地代码；不得从旧实现反推官方语义。
2. 写基础设施命令前，逐项核对模型、GPU、并行大小、缓存、连接器、代理、存储路径和容器生命周期参数。
3. 官方功能已有原生参数时，不增加自制代理、持久化目录或清理逻辑。
4. 对旧配置中的每个继承参数重新验证；不得因为它曾经运行过就默认保留。
5. 用户质疑设计原因时，先核对真实实现，再回答，不为未经验证的既有设计补充理由。
