FP8 (NVFP4 could cause looping, so formal training uses official FP8):
Current formal choice: Qwen/Qwen3.8-Flash-Next-FP8. The main model service responsible for prefill and decode uses physical GPU 0,2,5,7 with TP=4. The multimodal processor/vision encoder producer and Qwen3-VL embedding service share the separate physical GPU 4 at gpu-memory-utilization 0.45 each. Training keeps context_limit=262144 and reasoning_effort=medium; the vLLM backend uses a 20% compaction buffer with max_model_len=314573 and YaRN factor=1.2. TP=2 is not used because it previously left no available KV cache.

Build the formal training client image with ffmpeg because sample_video invokes it:

docker build -f docker/training/Dockerfile -t video-sql-training:7c6221d13f9f-0.3.0-ffmpeg docker/training

Formal training client Docker must include `--gpus all -e CUDA_VISIBLE_DEVICES=0,2,4,5,7 -e HOME=/root -e GIT_CONFIG_COUNT=1 -e GIT_CONFIG_KEY_0=safe.directory -e GIT_CONFIG_VALUE_0=/raid/wg25r/video_sql_v2` so W&B can monitor every GPU used by the three model services, read `/root/.netrc`, and let root read the mounted repository state.

The EPD image `video-sql-vllm-qwen38-flash-next-epd:current-device` uses `vllm/vllm-openai:qwen38-flash-next` and patches ECExampleConnector so each TP worker loads encoder cache onto its current CUDA device.

The formal EPD containers mount `/raid/wg25r/video_sql_v2/formal_runs/next_flash_fp8_epd_shared` at `/epd_shared`; vLLM shares `/epd_shared/cache`, and the proxy clears only that encoder cache after the active Responses request count reaches zero.
